# 第一点优化 v1.1：当前实验结果

更新日期：2026-09-04

## 1. 当前结论

在 MatMul128、单 seed 的精确合法种群配对实验中：

- CS 将凑齐相同未测合法种群所需尝试数从2048降到512，减少75%；
- 凑齐 quota 的时间从154.60秒降到112.34秒，加速1.38倍；
- 加上 H 后，完整搜索时间从223秒降到138秒，加速1.62倍；
- 相同16条真实 CUDA 测量预算下，tune 调用从788.04秒降到427.46秒，加速1.84倍；
- 两臂均无 build/run 错误；
- CS+H 的 best 和 top-k 更好，但这是单 seed smoke 信号，不能替代多 seed 质量结论。

因此，当前可以说：

> CS 是有效的搜索空间剪枝；当比较“产生相同数量完整合法候选并继续完成相同 GA、代价模型、编译和测量”的全流程时，本次配对中 CS+H 同时提高了合法候选产出效率和端到端速度。

## 2. 公平比较口径

两臂每个搜索批次的总初始种群都是128：

| 搜索批次 | 数据库已测候选 | 需要精确生成的未测合法候选 |
|---|---:|---:|
| 第1批 | 0 | 128 |
| 第2批 | 8 | 120 |

两臂都精确返回 `128 + 120 = 248` 条未测合法候选。随后执行相同的4代原生 GA，最终各测量16条程序。

固定条件：

```text
MatMul128 / CUDA sm_86 / seed 20260904
population 128 / GA 4 / mutation probability 0.85
16 trials / 8 trials per batch
XGBoost warmup 0：第二批使用第一批训练结果
soft off / draft off / GA-T2 off
```

两臂 `source_identity_sha256` 和加载的 DLL SHA256 完全一致。

## 3. 主要结果

| 指标 | Baseline | CS+H | 改善 |
|---|---:|---:|---:|
| 精确返回的未测合法候选 | 248 | 248 | 完全相同 |
| 初始化实际尝试数 | 2048 | 512 | 减少75.00% |
| 初始化完整通过数（含批尾富余） | 253 | 287 | — |
| 批尾富余丢弃 | 5 | 39 | — |
| 凑齐 quota 时间 | 154.598 s | 112.341 s | 1.376× |
| quota 产出速度 | 1.604条/s | 2.208条/s | 1.376× |
| 完整搜索时间 | 223 s | 138 s | 1.616× |
| VerifyGPUCode 时间 | 180.164 s | 127.014 s | 1.418× |
| Builder 时间 | 282 s | 138 s | 2.043× |
| Runner+模型更新 | 238 s | 125 s | 1.904× |
| tune 调用时间 | 788.039 s | 427.456 s | 1.844× |
| build errors | 0 | 0 | 相同 |
| runner errors | 0 | 0 | 相同 |
| 有限测量记录 | 16 | 16 | 相同 |

初始化完整通过率：

```text
Baseline = 253 / 2048 = 12.35%
CS+H     = 287 / 512  = 56.05%
```

因为以64条为微批次，最后一个批次可能多产生若干合法候选；这些候选被记录为 discarded，不进入 GA。这个批尾损耗反而对高通过率的 CS+H 更不利，但两边传给 GA 的数量仍严格相同。

## 4. 初始化与 GA 分阶段结果

| 臂/阶段 | generated | passed | Verify线程失败 | H提前拒绝 | shared失败 | lowering失败 | Verify时间 |
|---|---:|---:|---:|---:|---:|---:|---:|
| B / SampleInit | 2048 | 253 | 1615 | 0 | 139 | 41 | 132.262 s |
| CS+H / SampleInit | 512 | 287 | 0 | 0 | 154 | 71 | 109.233 s |
| B / Evolve | 992 | 864 | 86 | 0 | 31 | 11 | 47.751 s |
| CS+H / Evolve | 997 | 863 | 0 | 82 | 45 | 7 | 17.733 s |

这张表说明两件事：

1. CS 解决初始化生成问题：Baseline 为凑齐相同 quota 产生了1615次线程失败，CS 为0。
2. GA 仍会制造非法后代：Baseline 在 Evolve 中出现86次线程失败；CS+H 用 H-trace 提前拒绝82条，Evolve 的 Verify 时间从47.75秒降到17.73秒。

两边 GA 阶段的通过数几乎相同（864 对863），说明比较的后续 GA 工作量接近；主要差异来自初始化空间剪枝和变异后硬筛。

## 5. 最终测量质量

| 指标 | Baseline | CS+H |
|---|---:|---:|
| best | 114.228 µs | 49.226 µs |
| top-3 mean | 132.420 µs | 49.978 µs |
| top-5 mean | 140.244 µs | 53.984 µs |
| median | 166.220 µs | 168.709 µs |
| mean | 187.088 µs | 281.329 µs |

CS+H 的 best 延迟是 Baseline 的0.431倍，即本次约2.32倍 kernel speedup。top-3/top-5 同样明显更好，但中位数近似、均值更差，原因是 CS+H 的16条里仍有几个很慢的探索样本。因此严谨表述是：

> 本 seed 下 CS+H 的 top-k 搜索质量明显更好，但整个候选分布没有整体变好；需要多 seed 才能判断 top-k 改善是否稳定。

## 6. 与原固定512尝试 smoke 的关系

旧 smoke 固定两边都生成512次初始化尝试：

```text
Baseline 完整通过 68
CS 完整通过 304
```

因为 CS 让更多候选进入昂贵的 shared/lowering 检查，固定尝试数下 CS 的搜索时间反而更长。新实验回答的是不同且更贴近搜索目标的问题：

```text
为了获得相同数量的完整合法种群，各自需要多少尝试和时间？
```

结果显示，尽管单条线程合法候选的后续检查更贵，CS 仍以四分之一的尝试数和少27.33%的 quota 时间凑齐相同合法种群；再叠加 H 对 GA 非法后代的提前拒绝，完整搜索减少38.12%。

这两个结果并不矛盾：

- 固定原始尝试预算：CS 会做更多有意义但昂贵的后续检查；
- 固定合法种群目标：CS 不需要为线程非法候选反复扩大采样，整体更快。

## 7. Shared memory 的解释

CS+H 初始化的 shared-memory 失败为154，Baseline 为139，但分母不同：

```text
Baseline 到达线程约束之后的候选 = 253 + 139 + 41 = 433
shared 条件失败率 = 139 / 433 = 32.10%

CS+H 到达线程约束之后的候选 = 512
shared 条件失败率 = 154 / 512 = 30.08%
```

所以 shared 失败绝对数略多，不代表 CS 恶化了 shared 可行性。CS 只是让更多线程合法候选有机会到达下一层检查。

当前 pre-compaction shared proxy 仍有大量假阳性，本轮坚持只观察、不硬拒绝。

## 8. 仍不能下的结论

本轮只有：

```text
1 workload × 1 seed × 16 trials
```

因此尚不能声称：

- 跨算子通用加速；
- 多 seed 下最终性能稳定提升；
- CS+H 单独导致了2.32倍最终 kernel 性能提升；
- 定向 GA 或相对标签代价模型有效，因为二者本轮都关闭。
